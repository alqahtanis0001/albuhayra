**`docs/V12-SPEC.md` is authoritative and outranks this file.** This file records *how* §3 (and the v1.2b parts of §1) are built: lead decisions D1–D14, the reconciliation log (X1–X14) and the fixes from the reviewer's pre-code review (R-brief-b). Where this file and the spec ever disagree, the spec wins and this file is corrected with a Decision in `PROGRESS.md`. Strings: `src/i18n/ar.v12b.ts`. Schema: `prisma/schema.prisma` v1.2b block. Validation: `src/lib/validation/employees.ts`.

Checkpoints (single commits, no push; per spec §5 the lead continues without stopping except under §5):
- **CP1 — employees and salaries:** profile (party-linked), allowances, pay day, schedule fields, the «راتب شهري» plan, salary changes, ending/reactivating, «صرف راتب», salary privacy (spec §3.5), the owner payslip, the owner home order + quick actions (spec §1; «تسجيل حضور» arrives in CP2), the staff nav «حسابي».

## 1. Reconciliation with the spec (X1–X14)
Differences found between the earlier design / briefs / chat rulings and `docs/V12-SPEC.md`, each resolved **to the spec**:
- **X1 — «حضوري» is a staff nav item** (only for a linked login), not a card on the staff home (earlier design/R2 wording). The staff nav becomes الرئيسية | حركة جديدة | السجل | حضوري | حسابي (spec §1).
- **X2 — Staff nav gains «حسابي»** (`/staff/account`) for every staff login (spec §1); v1.2a had it only behind the top-bar name.
- **X3 — The link also grants "own salary instalments"** (spec §3.1): «حضوري» shows the employee's own salary months (due date, amount, paid, remaining, status) besides own attendance month and own payslips.
- **X4 — Salary category is رواتب, not selectable** (spec §3.2). The earlier design let the owner choose it. Resolved automatically: the establishment's OUT category named «رواتب»; if inactive it is reactivated, if missing it is created (both audited `CATEGORY_*` through the existing rules). `Employee.salaryCategoryId` stays in the schema as the resolved id; the form has no category field.
- **X5 — "Not stored" adds documents; the later item requires encryption at rest, masking and audited reveal** (spec §3.1). No field for ID/iqama, IBAN, date of birth, photos or documents exists in schema or validation.
- **X6 — Payslip footer** is exactly «هذه القسيمة ليست مستنداً رسمياً لحساب الأجور», and the payslip carries the **establishment header** (spec §3.4).
- **X7 — Self check-in** records **times only, for their own row**, on the server clock; the status is **derived from the times** (PRESENT, or LATE past start + grace); staff can never set غائب / إجازة / عن بُعد (spec §3.3). An owner override (`statusOverridden`) still wins, because the spec makes the computed status owner-overridable.
- **X8 — Salary privacy is settled by the spec (was "flagged for confirmation", D8):** hidden from every staff view — ledger, search, the staff المستحقات card, any staff-reachable list or export — are **payments of a salary plan's instalments and any «رواتب» entry linked to an employee party**; the only exception is the linked employee's **own** payslips and salary instalments on «حضوري». Aggregates on the staff dashboard may include them. A test asserts a staff session never receives another employee's salary-linked row (spec §3.5).
- **X9 — Owner home order and quick actions** (spec §1, a v1.2a mismatch fixed in CP1): quick actions (حركة جديدة · تسجيل دفعة → المستحقات · تسجيل حضور → today's daily sheet, CP2); the four money cards; «مستحقات هذا الأسبوع» with the red متأخرات strip; «الإضافات الجارية»; then balance by method, chart, top expenses, last entries. No employee widget.
- **X10 — Monthly grid and daily sheet** are both required (spec §3.3) — unchanged from the design.
- **X11 — "Staff canEdit does not apply to attendance"** (spec §3.3) — unchanged.
- **X12 — Checkpoint stops:** the earlier plan stopped for approval after each checkpoint; under the spec (§5 and the owner's instruction) the lead proceeds through v1.2b CP1, CP2 and v1.2c without stopping, except under §5.
- **X13 — Salary plan name** is «راتب شهري» (spec §3.2); the plan title is «راتب شهري — {party name}», derived from the party at read time so a rename follows.
- **X14 — Earlier chat ruling R3 said "category رواتب" and the design added a category field** — removed (X4).

## 2. Decisions (D1–D14; reviewer fixes marked ⟵ R-brief-b)
- **D1 — Salary plans:** `Plan.kind = SALARY`, `Plan.employeeId` (onDelete Restrict ⟵ N3), direction OUT, category = X4, system-managed: `updatePlan`, `cancelPlan` **and `archivePlan`** refuse `SALARY` (`err.salaryPlanManaged` ⟵ S1); the plan pages link to the employee instead. Payments, re-allocation, month locks and the revision lock are exactly v1.2a's.
- **D2 — Generation** through the end of next month, never before `Plan.startDate` and never after `endDate` (⟵ B2): `Plan.startDate` is set by the system to max(hire date, 1st of the current month) when a salary is first set, and to the 1st of next month on reactivation — **no backfill of past months** (an owner who needs a past month records it as an ordinary entry). A month is generated only if its pay date ∈ [plan start, end] and the employee has no `SalaryPeriod` for it. `@@unique([planId, periodYm])` + `SalaryPeriod @@unique([employeeId, periodYm])` make it idempotent; `SalaryPeriod` rows are created **without** `skipDuplicates` so a second concurrent plan aborts (⟵ S3). **Trigger (⟵ B1):** `ensureSalaryInstalments(estId)` wrapped in React `cache()` and awaited **first** in every page that reads salary data (owner home, المستحقات, plans list/detail, parties list/detail, `owner/staff/**`, `transactions/new?instalmentId`, «حضوري») and in the owner layout before `getOverdueCount`; on profile save inside the action. It fails safe: `ConcurrentChangeError` / P2002 → no-op, never breaks the render.
- **D3 — Pay date** = `payDay` clamped to the month's last day.
- **D4 — Snapshot per month** (`SalaryPeriod`: basic, allowances JSON — zod-parsed on read ⟵ N4 — gross). Instalment amount = gross − Σ deductions.
- **D5 — Salary changes affect future months only:** months whose pay date is after today and that are **unpaid** (paidHalalas = 0 and no non-deleted payment — ⟵ S4; v1.2a's "any reference incl. soft-deleted" predicate is kept only for *deleting* rows, because of the FK) are re-snapshotted. Transitions (⟵ S4): salary removed → unpaid future months deleted (FK-safe predicate), plan archived if nothing unpaid remains, else left OPEN without further generation; salary added later → plan created per D2; pay-day change → unpaid future months get the new due date and `seq` is recomputed from `periodYm` (⟵ N10); hire-date change after months exist affects only the lower bound of future generation; a new gross below a month's Σ deductions → `err.deductionExceedsGross`.
- **D6 — Ending employment:** `endEmployment(endDate)`, `endDate ≥ hire date` (`err.endBeforeStart` ⟵ S5). **Past end date (spec §3.2: "stops generation and archives the plan"):** delete unfixed months after `endDate` in the order deductions → periods → instalments (⟵ N5), then archive per v1.2a (write-off). The form lists unpaid months first with the write-off warning. **Future end date:** generation stops at it; status stays ACTIVE until the date passes, then ENDED (⟵ S5: attendance/check-in eligibility = ACTIVE and today ≤ endDate); when the date passes, `ensureSalaryInstalments` archives the plan per the spec — the end form states in advance that unpaid months will be written off on that date (⟵ B3, closed within the spec: the owner is told at the moment of choosing; the spec's "archives the plan" is kept). Reactivation clears `endDate` (⟵ S5) and opens a new plan from next month. Employee status changes are compare-and-set (`updateMany where status = …`, count 1) (⟵ S3).
- **D7 — Accrual for SALARY plans in balance and statement (⟵ B4):** balance = Σ amountDue(due ≤ today) − Σ paid over all rows (signed; a negative OUT remainder counts as لنا); the statement charges each instalment on its pay date when due ≤ today and lists every payment. Invariant tests on real SQL: advance on next month, rollover into a future month, archived salary plan.
- **D8 — Plan total** = Σ `amountDueHalalas` recomputed by aggregate after every salary row write inside the same `$transaction` (never by increment) (⟵ B5) — D2, D5, D6, D9 each have a test.
- **D9 — Deductions:** on an **unpaid** month (D5 predicate); Σ ≤ gross; updates the instalment + total under the revision lock and re-allocates; not subject to month locks.
- **D10 — Attendance records:** unique per employee-day; `statusOverridden`; hours computed at read; check-out after check-in (strictly later minute; same minute → `err.timeOrder` ⟵ N1); owner day save with scoped `findMany` → `createMany` + `updateMany`, rows carry the `updatedAt` they were loaded with and a changed row → `err.concurrentChange` (⟵ S9); P2002 mapped (⟵ S9).
- **D11 — Self check-in/out:** one `now` for date and time (⟵ N1); non-work day → PRESENT, no late; null grace = 0 when a start time exists (late = after start), no start time → PRESENT; second check-in → `err.alreadyCheckedIn`, P2002 → the same.
- **D12 — Payslip:** from `SalaryPeriod` + deductions; paid / remaining from the instalment's `paidHalalas` (after rollover this is what actually paid it), plus the payments recorded against it with date and method (⟵ S10).
- **D13 — Privacy predicate (X8)** — `salaryLinked(tx)` = `instalment.plan.kind = SALARY` **or** (`party.employee` exists **and** `category.nameAr = 'رواتب'`). Applied as an `AND: [{ NOT: … }]` clause, never a second `OR` (⟵ S2c — `ledgerWhere` already spreads an `OR` for `q`), in: the staff ledger rows + totals + search, staff recent lists, `getStaffDues`, `getStaffPaymentPrefill`, the staff edit page (`notFound()`), `updateTransaction`/`createTransaction` by STAFF on a salary entry or instalment (refused with the same key as a missing one — `err.instalmentInvalid` / `err.notFound`, no in-tenant oracle ⟵ N2, S2a). Real-SQL test: unlinked rows stay visible.
- **D14 — The employee's party is managed from the profile** (⟵ S6): the party pages refuse to retype, deactivate or delete a party linked to an employee (`err.partyIsEmployee`) and link to the profile. Adopting an existing unlinked موظف party passes its `partyId` (`EmployeeInputSchema.partyId`). Two active employees with the same name are refused by the inherited party rule (⟵ N11, accepted).

## 6. Amendments after the second R-brief-b (binding — Y1–Y12 override §2 where they differ)
- **Y1 — Generation starts at today, never in the past (replaces D2's lower bound).** `Plan.startDate` = max(hire date, **today**) when a salary is first set; the first month generated is the first pay date ≥ today. Reactivation and a salary re-added after removal set the **same** plan's (or the new plan's) `startDate` to max(hire, today); `Plan.startDate` never moves earlier (hire-date edits included). Reason: owners who recorded salaries as plain رواتب entries before v1.2b would otherwise get a phantom overdue month they cannot clear (cancel/archive refused on SALARY, relinking refused by `err.paymentLinkFixed`).
- **Y2 — D7 is dropped.** Salary plans use the v1.2a balance and statement semantics unchanged (spec §3.2 "via the v1.2a mechanism"): the balance counts every generated row, the statement charges the plan total on its start date. With Y1 and the one-month-ahead horizon, at most the next month is ahead of today. The v1.2a invariant (closing = party balance) holds by itself because payments ≤ total.
- **Y3 — D13 predicate, final:** `salaryLinked(tx)` = `instalment.plan.kind = SALARY` **or** (`party.type = EMPLOYEE` **and** (`category.nameAr = 'رواتب'` **or** `categoryId ∈` the establishment's `Employee.salaryCategoryId` values)). Covers v1.2a-era موظف parties with no profile (spec: "linked to an employee party") and a renamed salary category. Mutation-tested on both branches.
- **Y4 — STAFF may still add a plain «رواتب» entry to an employee party** (CLAUDE.md: "STAFF can always add entries"); it is then hidden from staff views like any salary-linked entry, including «حركاتي الأخيرة», and the staff form says so when that combination is chosen (`t.employees.staffHiddenNote`). Only a payment against a **SALARY instalment** is refused for STAFF.
- **Y5 — Grace (spec §3.3):** «متأخر» is computed only when a check-in time **and** a grace are set; a null grace → PRESENT; an explicit grace of 0 → late after the start time. (Replaces D11's "null grace = 0".)
- **Y6 — Lost-update guard is in the contract:** `AttendanceRowSchema.updatedAt` (optional ISO instant) echoes the row's `updatedAt` as loaded; a mismatch → `err.concurrentChange`.
- **Y7 — «صرف راتب» opens the current month's instalment only** (spec §3.2); none → `t.employees.noSalaryDue`.
- **Y8 — A SALARY plan reads جارية while its employee is ACTIVE,** even when prepaid (N6).
- **Y9 — Shapes:** `workDays` is one integer field (the day chips compute the mask client-side); `listLinkableStaff` = ACTIVE STAFF of the establishment with no linked employee, plus the current link; adopting a party overwrites its name/phone/email with the form's (the profile owns the party).
- **Y10 — The «رواتب» category is reactivated if inactive** (X4) and the form says so in one line (`t.employees.salaryCategoryNote`).
- **Y11 — «حضوري» generates only for the session's own employee:** `ensureSalaryInstalments(estId, ownEmployeeId)`.
- **Y12 — Gate conditions (spec §5), binding:** no edit to `scopeFailure`, `isReferenceProbe`, `LINK_KEYS`, `PROBE_SELECT_KEYS`, `UNIQUE_WRITE_METHODS`, `WHERE_METHODS`; new models only join the harness's model list; the W5 `paidHalalas` gate untouched and the generator never writes `paidHalalas` (not even 0) in `createMany`; admin patterns only tighten; any v1.2b call that would need a new exemption is a §5 stop.
- **Interpretation logged:** reactivation is not in the spec; it is kept as the inverse of the optional end date (spec §3.1).
