# v1.2c design — التذكيرات والتقارير (implementation of `docs/V12-SPEC.md` §4)

**`docs/V12-SPEC.md` is authoritative and outranks this file.** This file records *how* §4 (and §1's «التذكيرات» settings item) is built: lead decisions C1–C16. Where it and the spec disagree, the spec wins and this file is corrected with a Decision in `PROGRESS.md`. Strings: `src/i18n/ar.v12c.ts`. Schema: `prisma/schema.prisma` v1.2c block. Validation: `src/lib/validation/reminders.ts`. Fresh team (spec §5); reviewer reads the briefs before code; single-commit checkpoints; no push.

Checkpoints:
- **CP1 — the owner digest (§4.1):** Settings › التذكيرات (on/off + hour), `GET /api/reminders/run` protected by `CRON_SECRET`, one digest per owner per day, the Arabic email, `.env.example` + `render.yaml` + README.
- **CP2 — client reminders and reports (§4.2, §4.3):** per-party opt-in, «تذكير» by email or copy-ready WhatsApp text (explicit, audited), the aging report, the party statement to Excel and PDF, «بحسب الجهة» on the existing reports.

## Decisions (C1–C16)
**Digest (§4.1)**
- **C1 — Settings live on the establishment:** `Establishment.digestEnabled Boolean @default(false)`, `Establishment.digestHour Int @default(7)` (0–23, Asia/Riyadh). **Default off** — no email reaches an owner who did not ask for it. Settings › التذكيرات (`/owner/settings/reminders`, spec §1) with a switch and an hour select; `requireOwner()`; audit `DIGEST_SETTINGS`.
- **C2 — The endpoint** `GET /api/reminders/run` (route handler, the third API route; `docs/BACKEND.md`'s "only health and export" is amended by the spec). `CRON_SECRET` unset or empty → **503** with no body detail, and nothing else in the app depends on it. The secret is sent as `Authorization: Bearer <secret>`, compared with `timingSafeEqual` on equal-length buffers; wrong/missing → **401**. Never a query parameter (URLs end up in logs). `Cache-Control: no-store`. Response `{ ok: true, sent, skipped }` counts only — no establishment data.
- **C3 — Proxy allowlist:** `/api/reminders/run` joins `OPEN_PATHS` in `src/proxy.ts` (like `/api/health`) so an unauthenticated scheduler is not redirected to `/login`. **This adds one path to a list; the session logic is untouched** — the route's own `CRON_SECRET` check is its gate. Pinned in `proxy.test.ts`.
- **C4 — Who and when:** every establishment that is active, whose owner is ACTIVE and verified, with `digestEnabled`, whose `digestHour ≤` the current Riyadh hour, and that has no digest record for today (Riyadh date). A daily ping sends at ping time; an hourly ping honours each owner's hour (README).
- **C5 — At most one per owner per day, race-proof:** model `ReminderDigest { establishmentId, date @db.Date, status, itemCount, createdAt }` with `@@unique([establishmentId, date])`. The run **claims** the day with `create` first (P2002 → already claimed → skip), then builds and sends. Status `SENT` / `EMPTY` (nothing to report → **no email**) / `FAILED` (Brevo error — logged without secrets; not retried the same day: "at most one" wins over "eventually one"). Audit `DIGEST_SENT` attributed to the owner.
- **C6 — Contents:** OPEN plans' unpaid instalments (salary included — the owner's own data), both directions, grouped: **متأخرة** (due < today), **اليوم**, **غداً**, **خلال فترة التذكير** (due ≤ today + that plan's `reminderDays`, beyond tomorrow). Each row: party, plan (or «راتب شهري — name»), direction word لنا/علينا, remaining (Western digits, `formatSAR`), due date. Totals لنا / علينا per group. A link to `${APP_URL}/owner/dues`. At most 50 rows per group, then «و{n} أخرى» via `plural()`.
- **C7 — Owner-entered text in email is HTML-escaped.** v1.1e's A13 ("no user-supplied text in any email template") guards the auth emails, where an attacker controls the name; it stays for them. The digest shows the owner their own party names and plan titles, escaped with one helper, tested with `<script>` and quotes.
- **C8 — Scale and time:** the run processes establishments sequentially with a per-establishment try/catch (one failure never stops the rest); Brevo's free cap (300/day) is shared with auth mail — the digest respects the existing `mail:*` caps.

**Client reminders (§4.2)**
- **C9 — Opt-in per party:** `Party.remindersOptIn Boolean @default(false)`, toggled on the party page (owner only, audit `PARTY_REMINDERS`). No toggle, no reminder button anywhere.
- **C10 — Where:** a «تذكير» button on each unpaid instalment of an **IN** plan (the party owes us) of an opted-in party — plan detail and المستحقات (owner only; never staff). It opens a small dialog: **بريد إلكتروني** (only if the party has an email) and **نص واتساب**.
- **C11 — Email:** `sendClientReminder(instalmentId)` — `requireOwner()`, instalment in the establishment, plan OPEN and IN, instalment unpaid, party opted in and has an email; sends through Brevo with the establishment name in subject and body, the amount remaining and due date; **no reply-to** (the owner's login email is not exposed); caps: one email per instalment per day (`remind:{instalmentId}` via `consumeAttempt` with a day window) plus the existing `mailto:` cap; audit `CLIENT_REMINDER_EMAIL`. Refusals share one key per cause.
- **C12 — WhatsApp:** `prepareWhatsAppReminder(instalmentId)` — same checks; returns the text (Arabic, Western digits, establishment name, amount remaining, due date, plan title) and audits `CLIENT_REMINDER_WHATSAPP`; the dialog shows it with «نسخ». **No wa.me link and no phone handling** — copy-ready text only, as the spec says. Never automatic: both are button actions.

**Reports (§4.3)**
- **C13 — Aging:** `/owner/reports/aging` (a tab beside the existing report): overdue unpaid instalments of OPEN plans, by days past due into **0–30 · 31–60 · 61–90 · أكثر** (Western digits per §0), **لنا first, then علينا**, one row per party with the four buckets and a total, and totals per direction; printable. Salary instalments count under علينا.
- **C14 — Party statement to Excel:** `GET /api/export/statement?partyId=` (under the existing export route family; `requireOwner()`; reads only through `getPartyStatement` — no direct `db.` call, same rule as the ledger export; `Cache-Control: private, no-store`); one RTL sheet in the v1.1c style: title block, statement rows with running balance, closing balance, «حركات أخرى» below. Filename `statement_<party>_<date>.xlsx` (ASCII-safe fallback in `Content-Disposition`).
- **C15 — Party statement to PDF:** the existing printable statement, printed with the browser's «حفظ كـ PDF» — a «PDF» button calls `window.print()` with a one-line hint. No PDF library (the stack is frozen; the spec says "in the existing styles").
- **C16 — «بحسب الجهة»:** an optional party select on `/owner/reports`; `getReport(estId, from, to, partyId?)` and `/api/export?from=&to=&partyId=` filter by it (scoped; an unknown or foreign id → the unfiltered report is **not** shown — the page says the party is invalid).

## Security and tests
Rules 1/2b/10/11 on the new model and fields; admin sees nothing new; `CRON_SECRET` never logged or echoed; the endpoint returns counts only. Tests: 503 without the secret, 401 wrong/missing, 200 right (header only, query ignored); one digest per day under two concurrent runs (PGlite, the unique claim); hour gating across Riyadh midnight; grouping and dedupe; empty → no email; failed send recorded, not retried; escaping; opt-in required; IN-only; no staff path; caps; audit on every send; aging buckets at 30/31, 60/61, 90/91; statement export numbers equal `getPartyStatement`; party filter scoping; the migration on PGlite. Mutation-verify every gate.

## Amendments after R-brief-c (binding — override C1–C16 where they differ)
Reviewer: 3 BLOCKER, 10 SHOULD, 13 NOTE, all accepted; C3 judged **within spec §5** (one allowlist entry; `matches()`/`destinationFor`/session code untouched; the route never calls `requireX()`/`getSession`).
- **E1 (B1) — Selection is split from per-establishment work.** `src/features/reminders/select.ts` does only the cross-establishment selection and returns `{ establishmentId, ownerId, ownerEmail, name, digestHour }`; it is **excluded from the scoping gate's `FILES` with a named comment** (the admin precedent — the gate's rules are not changed) and has **its own static test**: receivers only `establishment`/`user`/`reminderDigest`, an explicit `select`, no financial model, no amount field. `digest.ts`/`run.ts` do per-establishment work and are **in `FILES`** with drivers: the claim `create` carries `establishmentId`; status updates are `updateMany({ where: { establishmentId, id } })`.
- **E2 (B2) — `PENDING` claim state** (schema updated): claim as PENDING, then `updateMany` to SENT/EMPTY/FAILED. A PENDING left by a crash means "outcome unknown" and is not retried that day.
- **E3 (B3) — Digest mail caps:** the digest does **not** use the per-IP `mail:` cap. It uses `mailto:{ownerEmail}` (`LIMITS.mailTo`) plus a **global daily digest cap of 150** (Brevo's free 300/day leaves 150 for auth mail). A capped digest is recorded FAILED and logged `[digest] capped` without the address. Mutation-proven.
- **E4 (S1) — Salary months are generated before building:** inside the per-establishment try, `runSalaryGeneration(estId, ownerId, today)` runs first (invoked, not changed); its `SALARY_GENERATE` audit gains `auto: true`.
- **E5 (S2) — Secret check:** sha256 both sides → `timingSafeEqual` on 32 bytes; exactly `Bearer <token>`; the env value trimmed, empty → 503; one identical 401 body for missing and wrong; `export const dynamic = "force-dynamic"`, Node runtime; headers never logged.
- **E6 (S3) — README (lead) requires an hourly free ping** with a ≥ 60 s timeout (Render cold start); a daily ping at hour H reaches only owners whose hour ≤ H, so it is not offered as an option.
- **E7 (S4) — Escaping** (`& < > " '`) applies to the HTML part only; subject and text parts stay raw with CR/LF and control characters stripped; the dues link uses `logoUrl()`'s protocol check and is omitted when `APP_URL` is unset.
- **E8 (S5) — Client-email "once a day" is durable:** eligible only if the scoped audit log has no `CLIENT_REMINDER_EMAIL` for that instalment since Riyadh midnight; the in-memory cap stays as double-click protection, consumed after eligibility and cleared if Brevo fails; **per-establishment cap of 20 client emails per day**.
- **E9 (S6) — Awaiting sends:** the client reminder and the cron route await the send; v1.1e A6's "never awaited" rationale (timing oracles) applies to auth flows only.
- **E10 (S7) — Party filter on the export** filters the ledger rows as well as the summary; the info sheet names the party (`t.reportFilter.exportParty`); `params.get()` null → undefined before the schema.
- **E11 (S8) — Statement filename:** ASCII `filename="statement_<partyId>_<date>.xlsx"` + `filename*=UTF-8''<encoded name>`; tested with an Arabic name, a quote and CR/LF.
- **E12 (S9) — Every claim outcome is audited** (`DIGEST_SENT` with `after = { date, status, itemCount }` only).
- **E13 (S10) — Client email footer** tells the client not to reply and to contact the establishment directly (value updated).
- **E14 (notes) —** N1 proxy pins (open with no session read; siblings still redirect; exact `OPEN_PATHS`; the `run/` folder holds only `route.ts`); N2 aging = days past due 1–30 · 31–60 · 61–90 · >90 (day 0 is not overdue), via `dayOffset` on ISO dates, one row per party per direction, OPEN plans only; N3 fixed in the schema; N4 reminder fields on `DueRow` only (`partyHasEmail: boolean`), `StaffDueRow` stays four keys; N5 one `now` → `todayISO(now)` + hour from `nowRiyadhHHMM(now)`, tested at 20:55Z and 21:05Z; N6 admin static patterns; N7 stale comments updated; N8 keys added; N9 exactly one ACTIVE verified OWNER, else skip + log without address; N10 concurrency = `Promise.all` of two runs on PGlite (mutations "P2002 as success" and "no claim" must fail); N11 group totals over all rows; N12 recipients are owner emails only, no cross-establishment names; N13 the user sees C1/C5/C15 in the report.
